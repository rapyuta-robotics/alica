# Plan designer: design

Status: agreed design, not built yet. It builds on `alicaplan` ([alicaplan.md](../alicaplan.md)).

Deep plan trees with blackboards and key mappings between parents, children and conditions are
hard to follow as files. The designer shows the plan hierarchy from the master plan down, gives
each plan its own view, and later edits plans.

## Source of truth

- The `*.alica.yaml` modules are the only source. Agents and the designer both edit them; the
  engine JSON is generated by `alicaplan compile` and never edited by hand.
- Positions are stored in `<module>.layout.yaml` next to the module, one entry per entry point,
  state and synchronisation, plus transition bend points. You can arrange a plan by hand;
  **Auto-arrange** lays it out with ELK and saves the result; **Snap to grid** keeps hand
  placement tidy; **Lock layout** stops accidental drags. Elements without a stored position
  (for example ones an agent just added) are placed automatically around the placed ones.

## Architecture

- `alicaplan serve SRC`: a local Python server that reuses the compiler and checker. It loads the
  modules into one resolved model, runs the checks, serves the model to the browser, and watches
  the files so edits from agents show up live.
- Edits from the browser are operations ("add transition A -> B with condition X"). The server
  applies them, re-checks, and writes the YAML back with ruamel.yaml so comments and formatting
  survive.
- Frontend: TypeScript, React, React Flow for the canvas, ELK for layout. The built files ship
  inside the Python package.

## Screen

Three panes:

- **Left: hierarchy.** Starts at the master plan and follows state -> children. Plans can be
  reused, so this is a graph shown as a tree with "used N times" badges and a jump between
  uses. Below it, the library: behaviours, plans, plan types, placeholders, tasks, roles and
  conditions, each with its "used in" list. Items are dragged from here onto states.
- **Middle: the selected plan's canvas,** with a breadcrumb of the path from the master plan.
  Double-clicking a plan or plan type child opens that plan.
- **Right: inspector** for the selected element: properties, blackboard, and key mappings.
- **Bottom: problems** from the checker; clicking one selects the element.

A plan has a second tab, **Data flow**: its blackboard keys on the left, each child and each
transition condition as a column of its input and output keys, and the key mappings as wires.
Type mismatches are drawn red. **Trace key** highlights where one value travels up and down the
whole hierarchy.

A **Roles** view shows the role x task priority grid; a plan's roles tab filters it to the
plan's entry-point tasks.

## Canvas

- **State:** a solid circle of one fixed size with the state icon, filled in the foreground
  color, with the state name above it. The state's children hang below it on a solid spine,
  one row each. Transitions connect circle to circle, so their routing does not depend on how
  many children a state has. Auto-arrange treats the hanging column as part of the state's
  footprint. Dragging the circle moves its children with it.
- **Success and failure states:** the same circle, filled green (success) or red (failure),
  labelled "Success" or "Failure". A named terminal state shows its name as a smaller second
  line. Green and red are used for nothing else except checker errors.
- **Master plan:** has no success or failure states; the palette does not offer them, and the
  checker reports them as errors.
- **Entry point:** a pill with the task and cardinality, `Attack [1..1]`, wired to its initial
  state.
- **Transition:** an arrow with a condition badge in the middle. The badge shows the condition
  name and the number of keys mapped into the condition's blackboard (`⇢2`); clicking it opens
  the condition's blackboard and mappings in the inspector.
- **Synchronisation:** a short orange bar across each synchronised transition, with the
  synchronisation's name.
- **Child row:** icon, name, and the mapping count (`⇢2 ⇠1`); unresolved or mistyped mappings
  are shown in red on the row.
- **Plan header:** the plan name, pre-condition, runtime condition and utility threshold.

## Visual language

Every kind has an icon (Lucide) and a color:

| Kind                 | Icon            | Color                          |
| -------------------- | --------------- | ------------------------------ |
| Plan                 | `workflow`      | violet `#8b5cf6`               |
| Behaviour            | `cog`           | teal `#14b8a6`                 |
| Plan type            | `layers`        | pink `#ec4899`                 |
| Placeholder          | `square-dashed` | gray `#94a3b8`, dashed outline |
| Transition condition | `diamond`       | amber `#f59e0b`                |
| Pre-condition        | `shield-check`  | amber                          |
| Runtime condition    | `activity`      | amber                          |
| Post-condition       | `flag`          | amber                          |
| Synchronisation      | `link`          | orange `#f97316`               |
| Entry point / task   | `log-in`        | sky `#0ea5e9`                  |
| Role                 | `user`          | lime `#84cc16`                 |
| Blackboard key       | `database`      | neutral gray                   |
| State                | `circle-dot`    | foreground                     |
| Success state        | `circle-check`  | green `#22c55e`                |
| Failure state        | `circle-x`      | red `#ef4444`                  |

In live mode agents are marked with outlines and small agent badges, not fills, so the kind
colors keep their meaning.

## Phases

1. **D0, read-only viewer:** hierarchy, plan canvas, inspector, problems, live reload from files.
2. **D1:** data flow view and key tracing.
3. **D2:** editing: add, rename and delete states, transitions and entry points; drag children
   onto states; key mappings with type-filtered dropdowns; project-wide rename; turn selected
   states into a new child plan; undo and redo. Every edit goes through the checker.
4. **D3, live mode:** the same canvas attached to running engines, highlighting each agent's
   current state and entry point.
